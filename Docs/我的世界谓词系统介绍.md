# 我的世界谓词系统介绍

## User

你知道我的世界的谓词系统吗

---

## Assistant

知道。Minecraft 的**谓词（Predicate）**是 1.15 引入的**数据驱动条件系统**，本质就是把「一堆 if 判断」写成 JSON，然后用命令、进度、战利品表、物品修饰器等地方复用。

## 1. 文件位置与命名

```
data/<命名空间>/predicate/<名字>.json     ← 1.21+ （单数）
data/<命名空间>/predicates/<名字>.json    ← 1.20.6 及以前（复数）
```

引用时写作 `命名空间:名字`，例如 `mypack:is_sneaking`。

顶层字段用 `"condition"` 指定谓词类型（和战利品表条件完全同源）：

```json
{
  "condition": "minecraft:entity_properties",
  "entity": "this",
  "predicate": { "type": "minecraft:player" }
}
```

## 2. 可以用在哪

| 场景 | 写法 |
|---|---|
| 命令 | `/execute if predicate mypack:is_sneaking run ...` |
| 目标选择器 | `@e[predicate=mypack:is_sneaking]` |
| 战利品表 | `"conditions": [{"condition":"minecraft:reference","name":"mypack:foo"}]` |
| 进度（advancement） | 各触发器的 `conditions` 里 |
| 物品修饰器 / 其它 | 通过 `minecraft:reference` 复用 |

## 3. 主要谓词类型

**逻辑组合**
- `all_of`（字段 `terms`）、`any_of`（`terms`）、`inverted`（`term`）
- `reference`（`name`，引用另一个谓词文件）

**随机类**
- `random_chance`（`chance`: 0~1）
- `random_chance_with_looting`（`chance` + `looting_multiplier`）
- `table_bonus`（`enchantment` + `chances` 数组）
- `survives_explosion`

**实体类**
- `entity_properties`：`entity`（上下文实体名）+ `predicate`
 - 子字段常用：`type`（实体 ID / `#标签`）、`nbt`、`flags`（`is_sneaking`、`is_on_fire`、`is_baby`、`is_sprinting`、`is_on_ground`、`is_flying` 等）、`equipment`（`mainhand`/`offhand`/`head`/`chest`/`legs`/`feet`）、`effects`、`distance`、`location`、`vehicle`、`passenger`、`targeted_entity`、`stepping_on`
 - `entity` 常见取值：`this`，以及某些上下文里的 `killer`、`direct_killer`、`attacker`、`player_killer`
- `entity_scores`：`entity` + `scores`（记分板，值可写 `{"min":1,"max":5}`）
- `killed_by_player`（`inverse`）

**位置/世界类**
- `location_check`：`offsetX/Y/Z` + `predicate`
 - location 子谓词：`position`、`dimension`、`biomes`、`structures`、`light`、`block`（`blocks`/`state`/`nbt`/`tag`）、`fluid`、`smokey`、`can_see_sky`
- `weather_check`：`raining`、`thundering`
- `time_check`：`value`（范围）+ `period`
- `block_state_property`：（方块战利品表里）`block`、`properties`

**物品/数值/伤害类**
- `match_tool`：`predicate`（item predicate：`items`、`tag`、`count`、`durability`、`enchantments`、`stored_enchantments`、`nbt`、`components`）
- `value_check`：`value`（数字提供器，如 `{"type":"minecraft:score",...}`、`enchantment_level`、`uniform`）+ `range`
- `damage_source_properties`：`tags`（伤害类型标签）、`source_entity`、`direct_entity`、`is_direct`

较新版本还加了 `environment_attribute_check`（环境属性检查，1.21.5+）、`enchantment_active_check` 等。

## 4. 完整示例

`data/mypack/predicate/rainy_veteran.json`

```json
{
  "condition": "minecraft:all_of",
  "terms": [
    {
      "condition": "minecraft:entity_properties",
      "entity": "this",
      "predicate": {
        "type": "minecraft:player",
        "flags": { "is_sneaking": true }
      }
    },
    {
      "condition": "minecraft:entity_scores",
      "entity": "this",
      "scores": { "kills": { "min": 10 } }
    },
    {
      "condition": "minecraft:location_check",
      "predicate": { "dimension": "minecraft:overworld" }
    },
    {
      "condition": "minecraft:weather_check",
      "raining": true
    },
    {
      "condition": "minecraft:random_chance",
      "chance": 0.25
    }
  ]
}
```

使用：

```mcfunction
execute if predicate mypack:rainy_veteran run say 你满足条件了
tellraw @a[predicate=mypack:rainy_veteran] {"text":"老兵"}
```

## 5. 容易踩的坑

- **目录名**：1.21 起所有数据包目录改单数（`predicate/`、`function/`、`loot_table/`、`advancement/`、`tags/entity_type/`…），旧包直接报错。
- **上下文实体**：`this` 只在有「主体」的上下文才存在；战利品表里能不能用 `killer` 取决于表类型（方块表 vs 实体表）。
- **字段形如列表**：`items`、`blocks`、`type` 等在 1.20.5+ 大多可写 ID 或 `#标签` 的列表，旧版本限制更严。
- **`nbt`/`potion`**：1.20.5 物品组件化后基本改用 `components`，老写法失效。
- 谓词只能做**判断**，不能执行逻辑；要「或/且/非」就靠 `any_of`/`all_of`/`inverted` 组合。

# 给 RimWorld 设计谓词系统

先说个前提：RimWorld **已经有一堆"半个谓词系统"**了 —— `ThingFilter`、`PawnGroupMaker`、`ScenPart`、`QuestScriptDef` 的节点树、`HediffGiver`、`StatWorker`、`Alert`、`RitualOutcomeEffect`，全都是"条件 + 结果"的不同方言。所以真正的设计目标不是从零造，而是**抽出一套统一的、可组合的、数据驱动的条件原语**，让这些系统共用一套语法，并且让 mod 作者不必再写 Harmony patch 就为了加一句 `if`。

---

## 一、先定"谓词作用在谁身上"（上下文模型）

RimWorld 不像 Minecraft 只有"玩家/实体"一个主体，它的世界是分层的。谓词的 Context 至少要能携带这些 Subject：

| 层 | Subject | 典型可测字段 |
|---|---|---|
| 生物 | `Pawn` | race/def、xenotype、基因、年龄阶段、性别、特性、技能等级与热情、`PawnCapacityDef`（Moving/Manipulation/Consciousness…）、hediff 及严重度、缺失肢体/仿生体、心情与心态、精神崩溃状态、需求条、着装与装备、随身物品、社交关系、意识形态（precept/meme/role）、头衔爵位、怀孕、tattered、允许区域、工作类型是否启用 |
| 物品 | `Thing` | def、defName tag、`ThingCategoryDef`、stuff/材料、`QualityCategory`、耐久百分比、是否被污染/腐烂、`comp` 的存在与状态、叠加数量、市场价值、是否被禁用/预定、是否属于某收藏库存 |
| 地图 | `Map` | biome（及 biome tag）、温度、天气、季节、污染、屋顶覆盖率、财富、危险度、居民数、是否夜间、是否有敌对区域 |
| 格子 | `Cell` / `TerrainDef` | 地形、肥沃度、光照、屋顶、可通行、美饰度、清洁度、雪/水、是否在房间内、视野遮挡 |
| 房间 | `Room` | `RoomRoleDef`、尺寸、`RoomStatDef`（impressiveness/cleanliness/beauty）、温度、包含物、是否囚房/仪式厅 |
| 世界 | `WorldObject` / `Tile` / `Faction` | 地块特征、道路、定居点、派系关系、行星类型、是否已探索、距离 |
| 时间 | — | tick、日/小时、象限（quadrum）、季节、故事讲述者阶段、冷却是否过期 |
| 意识形态 | `Ideo` | meme、结构、风格主导度、仪式结果、圣物 |

另外要区分 **Actor（执行者）、Target（被作用者）、Observer（观察者/玩家）**——比如"给监狱里最不满的囚犯加个想法"，主体、目标、范围是三个不同的东西。

## 二、谓词原语：哪些"操作"是必须的

### 1. 逻辑组合
`all_of` / `any_of` / `none_of` / `not`，要求**短路求值**（性能命脉）。

### 2. 属性断言
```
<StatValue Stat="MoveSpeed" Value=">=4.5"/>
<SkillLevel Skill="Crafting" Level=">=8"/>  ← 也支持 passion
<Capacity Level="Manipulation" Min="0.5"/>
<HasHediff Def="Flu" Severity=">0.6"/>
<Trait Trait="Pyromaniac"/>  ← 可 any/all/none
```

### 3. 集合与标签
RimWorld 的 `thingCategories` / `tradeTags` / 自定义 `defName` tag 是天然的谓词词汇表。
`RequiresAny(tag)`、`RequiresAll(tag)`、`Excludes(tag)`、`InCategory(def)`。

### 4. 数值与范围
除了 min/max，最好支持**双向范围、开闭区间、百分比**，并且能引用别的 Def 的字段（如"耐久 < `MaxHitPoints` 的 30%"）。

### 5. 随机与权重
- `Chance`（可带 modifier，比如按运气/技能/难度修正）
- **确定性**很关键：随机必须走 `ctx.Rand`（seed 化），否则读档、多人、回放会不一致。

### 6. 存在量词与空间查询 ← **RimWorld 最缺、最该有的一环**
```
<AnyCell Radius="12" Predicate="RoofedAndNotSnowy"/>
<CountPawns Radius="20" Kind="Prisoner" Predicate="Mood&lt;0.2" Min="3"/>
<NearestThing Def="SteamGeyser" Within="30"/>
<Reachable Target="..."/>
```
把这层做出来，很多"我需要在 C# 里遍历 region 找位置"的需求就消失了。

### 7. 时间性与状态机
- `HeldFor(duration)`：条件**持续了 N 天**才成立
- `Cooldown`、`OncePer(target)`、`CooldownGlobal`
- `SinceLastFired`、`InGameCondition("ToxicFallout")`

### 8. 组合与复用
`PredicateRef`（引用另一个谓词 Def），支持 `ParentName` 继承 —— 这是让 XML 不爆炸的唯一办法。

## 三、谓词驱动的"操作"（用途层面）

谓词本身只做布尔判断，但接上不同的宿主系统就能干不同的事。我建议按 **Match / Select / React** 三层来设计：

### A. Match —— 判断（能不能）
- `IncidentDef` 的 `canFireNow`
- `RecipeDef` / `Bill` / `WorkGiver` 是否可用
- `Alert` 何时显示
- `Gizmo` / 按钮 / 指令何时可用
- 囚犯是否可招募、奴隶是否可解放、动物是否可驯服
- 任务（Quest）节点是否可生成

### B. Select —— 筛选与排序（选哪个）
这层 RimWorld 需求比 Match 更重：
- **筛选**：`ThingFilter`、库存策略、服装规则、账单搜索范围、商队装货
- **选择**：事件选 pawn、AI 选目标、遗物选效果对象 —— 需要"谓词 + 评分函数"
- **排序**：`Score`/`SelectionWeight` 函数（加权随机）

所以设计上 **谓词一定要和 `Weight`/`Score` 配对**，而不是只有 true/false。

### C. React —— 规则（谓词 + 动作）
这是收益最大的部分：把"条件 → 副作用"做成数据驱动的规则 Def，就能替代大量 C# / Harmony。

可用动作大致有：
| 动作 | 效果 |
|---|---|
| `AddHediff` / `RemoveHediff` | 加病、加伤、移除 |
| `AddThought` / `SetMood` | 心理层面 |
| `SpawnThing` / `SpawnPawn` | 生成 |
| `FireIncident` | 触发事件（突袭、空投、事件链） |
| `SendSignal` | 与 `CompSignal` 体系对接，打通现有异步逻辑 |
| `ChangeRelation` / `SetFaction` | 外交与身份 |
| `AddGene` / `SetXenotype` | 生化层 |
| `UnlockResearch` / `GrantAbility` | 进度层 |
| `GiveLoot` | 掉宝（相当于 Minecraft 战利品表） |
| `ShowLetter` / `ShowDialog` | 叙事反馈 |

**关键约束：谓词绝不应该有副作用。** 规则才是"条件+动作"。这条分界线一旦模糊，就会变成难以调试的混乱（Minecraft 的 advancement 之所以好用，正是因为它严格分开了 trigger / conditions / rewards）。

## 四、Schema 长什么样（XML 示例）

```xml
<PredicateDef>
  <defName>Pred_WealthyLowPop_Night</defName>
  <label>富有但人少（夜间）</label>
  <subject>map</subject>
  <li Class="AllOf">
    <terms>
      <li Class="StatValue"   Stat="Wealth"   Value=">=50000"/>
      <li Class="PawnCount"   Kind="Colonist" Max="4"/>
      <li Class="TimeOfDay"   From="20" To="5"/>
      <li Class="Not">
        <term Class="GameCondition" Def="ToxicFallout"/>
      </li>
      <li Class="Chance" Value="0.35"/>
    </terms>
  </li>
</PredicateDef>
```

宿主使用：

```xml
<IncidentDef>
  <defName>Raid_DesperateAmbush</defName>
  <predicate>Pred_WealthyLowPop_Night</predicate>
  <selectionWeight>1.5</selectionWeight>
</IncidentDef>
```

规则示例：

```xml
<RuleDef>
  <defName>Rule_BreakAndBurn</defName>
  <when Class="AllOf">
    <terms>
      <li Class="PredicateRef" Def="Pred_WealthyLowPop_Night"/>
      <li Class="AnyPawn" Kind="Colonist">
        <predicate Class="Mood" Max="0.15"/>
      </li>
    </terms>
  </when>
  <then>
    <li Class="FireIncident" Incident="MentalBreak_Wild"/>
    <li Class="ShowLetter" Text="有人撑不住了。"/>
  </then>
</RuleDef>
```

## 五、工程实现上的几个硬约束

1. **两阶段加载**：XML 解析成 Def，然后在 `DefDatabase` 加载完成后统一做**引用校验**（找不到的 defName、tag、skill 要在启动时报错并指出文件行号）。RimWorld 的 XML 校验体验是它的强项，谓词系统必须继承。
2. **静态/动态分离**：只依赖 Def 的谓词（如"是动物"）可以在加载期预计算/剪枝；依赖运行时状态的不能。混在一起会让性能崩。
3. **性能**：谓词会被高频调用（每 tick 的 work scan、每帧 UI、每次筛选）。必须：短路、缓存 + 脏标记、禁止 LINQ 与装箱、给谓词标 `cheap/expensive` 并允许采样。
4. **确定性**：所有随机走 context 的 RNG，禁止 `Rand.Value`。否则多人/回放/读档会漂移。
5. **可解释性**：调试工具必须能回答"**为什么没匹配**"——递归打印每一层的实际值与期望值。这是数据驱动系统能否被 mod 作者接受的决定性因素。
6. **不要重造轮子**：`StatDef`、`PawnCapacityDef`、`ThingCategoryDef`、`PawnRecordDef`（1.4+ 的记录系统）、`RoomStatDef` 已经是很好的词汇表，谓词应该是它们的**薄封装 + 组合器**，而不是平行的新体系。
7. **序列化**：规则/谓词要能存进存档（Scribe），否则运行时动态生成的规则会读丢。

## 六、一个容易忽略的设计洞察

RimWorld 的核心不是"满足条件就发生"，而是**"在众多候选中挑选一个最有故事性的"**。所以真正好用的谓词系统，形态应该是：

> **Query = Scope（作用域/量词） + Predicate（过滤） + Score（评分） + RNG（确定性随机） + Cooldown（节奏）**

只做 `bool` 的谓词系统在这里会用力不足；把它提升成"查询 + 打分"的 DSL，就能同时覆盖 Stockpile 筛选、事件选择、AI 选目标、任务生成这四件最耗 mod 作者精力的事。

# 结论先说：和 MC 谓词只重合 **1/3**

MC 的谓词（predicate）**只是条件层**，它回答的是「现在是否满足 P」。它没有触发器、没有动作、没有变量绑定、没有生命周期。

你描述的这套东西 —— **事件发生时，把某些实例绑定到变量，满足条件就执行一串会失败、会中断、需要重试的操作** —— 这在计算机科学里叫 **ECA 规则引擎 / 反应式自动化系统（Event–Condition–Action）**。MC 里对应它的完整形态是：

| 你要的能力 | MC 里的对应物 | RimWorld 里需要自己造吗 |
|---|---|---|
| 条件判断 | **predicate** | 有半个（ThingFilter/StatDef/QuestNode） |
| 事件触发 | 无（只有 tick 轮询 + `/schedule`） | ❌ 完全要造 |
| 目标选择 | `@e[predicate=...]` 选择器 | 有半个（PawnGroupMaker/ListerThings） |
| 变量绑定 | 无 | ❌ 要造 |
| 动作执行 | **function / 命令** | 有半个（Job/ThinkTree） |
| 生命周期/仲裁 | 无 | ❌ 要造，且最难 |

所以你的直觉是对的：**谓词只是你系统里最不值钱的那 30%**。真正决定这东西能不能「爆火」的是另外 70%。

## 一、四根支柱，缺一不可

```
When（触发器）→ Where/Who（绑定查询）→ If（条件）→ Then（动作 + 它的生命周期）
```

### 1. When —— 触发器：事件驱动 + 电平驱动，两者语义完全不同

| 模式 | 语义 | 例子 |
|---|---|---|
| **边沿触发（Edge）** | 状态**发生变化的那一刻**触发一次 | 袭击开始、小人死亡、天气变为下雨 |
| **电平触发（Level）** | 只要条件**持续为真**，就一直想执行 | 餐厅温度 < 0℃、某小人没穿衣服 |
| **序列触发（CEP）** | A 发生后 5 秒内又发生 B | 有人倒地 → 3 秒内又有人倒地 |

初学者写规则，90% 的 bug 都来自把这两种搞混：写成电平触发，动作又没做幂等，就会每 tick 刷一次屏。**引擎必须在语法上就把它们区分开**（`<OnEvent>` / `<WhileTrue>`），而不是让玩家自己猜。

RimWorld 的事件源清单（这部分要做全，否则玩家会觉得「什么都触发不了」）：

- 地图/世界：RaidBegan、IncidentFired、WeatherChanged、SeasonChanged、GameConditionStart/End、MapGenerated、ToxicFallout
- Pawn：Spawned、Died、Downed、HediffAdded、MoodBelow、MentalBreak、InventoryChanged、EnteredMap、RelationshipChanged、DraftedChanged
- Thing：Spawned、Destroyed、QualitySet、TemperatureChanged、Deteriorated、CountChanged
- Room：RoomTemperatureCrossed、RoomRoleChanged、RoomImpressivenessCrossed
- 时间：每 N tick、每日某时刻、随机间隔
- 玩家：SelectionChanged、OrderIssued（玩家指令应该能抢占规则）
- 状态量：任何可求值的谓词都能当电平触发源

### 2. Who/Which —— 绑定与查询：这是 RimWorld 特有的最大难点

你的例子「小人 a 去拿冲锋枪打袭击者」里藏了三个查询：

- `$pawnA` —— **单例绑定**（a 是哪个？固定名字？还是「射术最高且空闲的殖民者」？）
- `$gun` —— **单例绑定 + 可达性**（枪在哪？在仓库里？被禁用了？被谁预定了？)
- `$raiders` —— **集合绑定 + 持续更新**（袭击者是动态集合，会死会增援）

所以查询语言至少要支持：

```
Query Pawn
  where faction == Hostile AND map == $home AND !downed
  order by distance(sqrt to $pawnA)
  take 1          // 或 take all / take random 1 / take highest(Shooting)

Query Thing
  where def.tags contains "Gun" AND stuff == Steel
  where reachableFrom($pawnA) AND !forbidden AND !reserved
  order by hitPointsPercent desc
  take 1
```

关键点：

- **`reachableFrom`** 是 MUST。RimWorld 是格子世界，不考虑寻路的「去拿枪」会立刻卡住。
- **集合绑定要能「重新求值」**：袭击者死了一个，`$raiders` 要自动缩小。绑定不能是快照，得是活的查询句柄。
- **量词是刚需**：`any` / `all` / `none` / `count(>=3)` / `argmax`。RimWorld 里「地图上是否存在一个能站、能睡、非屋顶的格子」这种需求遍地都是。
- **空间谓词**：半径、邻接、视线、屋顶、区域（AllowedArea）、区域连通性。

### 3. If —— 条件（谓词）在这里，和 MC 的差不多

这一层你确实可以大量借鉴 MC 的谓词设计：逻辑组合、数值区间、标签匹配、概率、`reference` 复用。但要额外加两样 MC 没有的：

- **`duration` 包装**：条件**持续了多久**才成立（「连续 2 天没吃东西」）
- **`hysteresis`（滞回）**：开阈值和关阈值分开，防止抖动 —— 你举的「下雨导致餐厅温度归零」正是典型：

```xml
<Rule defName="Rule_HeatDiningRoom">
  <whileTrue> <AllOf>
      <Weather Is="Rain"/>
      <RoomTemp Room="$dining" Operator="&lt;" Value="10"/>
  </AllOf></whileTrue>
  <then> <Ensure Thing="$heater" Powered="true"/> </then>
  <hysteresis On="10" Off="15"/>   <!-- 10℃ 开，回升到 15℃ 才关 -->
</Rule>
```

没有滞回，加热器会每 tick 开关开关，玩家会觉得你写的系统很蠢。

### 4. Then —— 动作：RimWorld 里动作**不是原子的**

这是和 MC 差别最大的地方。MC 的 `/give` 是瞬时、必成功、不可中断的。而你的「去拿冲锋枪」在 RimWorld 里是：

```
判定 → 寻路到枪 → 拿起（可能被击倒/被截断）→ 换装（可能被别的 job 抢占）→
寻路到坐标 → 进入战斗 → 目标死了 → 重新选目标 → 弹药/血量耗尽 → 撤退
```

所以动作系统需要三种语义：

| 类型 | 语义 | 适用 |
|---|---|---|
| **Command** | 下发一次 job，不管后续 | 「立刻打这个目标」 |
| **Maintain（不变式）** | 维持目标状态，被中断就自动重试，直到不再需要 | 「保持装备冲锋枪」 |
| **Sequence/Task** | 有步骤、有前置、可失败可回滚 | 「拿枪 → 去坐标 → 战斗」 |

而且**每个动作必须能报告失败原因**（不可达 / 目标已死 / 被玩家指令打断），否则玩家无法调试。

还有一个 RimWorld 特有的坑：**你的动作是在和 Pawn 的 ThinkTree 抢控制权**。如果不处理，小人拿到枪之后转头去吃饭了。所以动作层必须能声明：

- 是否**锁定**该 Pawn 的行为（类似「强制 job」）
- 何时**让渡**（更紧急的：起火、流血、玩家指令、自己倒地）
- 优先级/抢占规则

建议给所有动作加统一的三字段：`Priority` / `YieldTo` / `InterruptPolicy`。

- **Thing**：生成/销毁、改数量、改材料/品质、移动、设 forbidden、改温度
- **地图/世界**：改天气、改温度、触发事件、改派系关系、解锁研究、发信件、播放音效、发信号（对接 `CompSignal`）

## 三、九个会决定成败的工程点

1. **终止性**：动作改变状态 → 再次触发规则 → 死循环。必须有：边沿/电平区分、`Cooldown`、滞回、规则链深度上限、单 Pawn 同时活跃规则数上限。
2. **仲裁**：两条规则同时想控制同一个 Pawn 怎么办？需要优先级 + 层级（玩家指令 > 紧急 > 自动化 > 默认）。
3. **确定性**：所有随机必须走存档绑定的 RNG，否则读档/多人会不一致（RimWorld 的随机在存档里是有状态的，别用 `Rand.Value` 裸调）。
4. **性能**：不要「每 tick 遍历所有规则 × 所有实例」。要事件订阅 + 空间索引 + 脏标记 + 谓词成本分级（cheap / expensive），expensive 的允许降频采样。
5. **序列化**：规则存在存档里（Scribe），也要能导出分享。
6. **沙箱**：玩家写的规则**不能**执行任意 C#。动作必须是白名单化的类型 + 强类型参数（RimWorld 的 XML `Class=` 是能执行任意代码的，别把这个暴露给玩家）。
7. **调试器**（最重要）：为什么没触发？为什么触发了没生效？需要一条时间线：「12:03:11 Rule#3 触发 → 绑定 $pawnA=张三 → 条件通过 → 动作 Equip 失败：目标被 Reserved by 李四」。**没有这个，玩家写不出超过 3 条规则的东西。**
8. **可视化 + 模板库**：方块式编辑器 + 一键订阅的规则包（「袭击响应」「自动供暖」「自动灭火」「伤员优先送医」）。这是「爆火」的真正载体 —— 玩家分享的是**规则蓝图**，不是代码。
9. **模拟/试运行**：能对当前存档做「如果现在触发会怎样」的干跑，不改动状态。

## 一、四条语法原则

1. **一个模型，两种视图。** 文本是规范形式（可 diff、可上工坊、可让 AI 生成），方块是它的渲染。绝不能设计两套。
2. **动词优先的受限领域语言。** 不做通用编程语言。宁可 `做 X 对 Y` 这样又笨又好懂，也不要 `map/filter/lambda`。
3. **每个槽位都是"实例引用"，且可预览。** 槽位的三种形态统一：点名实例 / 查询 / 变量。编辑器一律允许点开看。
4. **失败是第一公民。** 每个块都能回答「我做到了吗？没做到为什么？」

## 二、双层语法，同一个底层

### 简易层（默认给玩家看）

```
┌ 当〔袭击开始〕于〔家园〕 ──────────────────
│  设〔守卫〕 = 找 1 个〔能战斗的殖民者〕      🔍
│  设〔枪〕   = 找最近的〔远程武器〕可到达〔守卫〕 🔍
│
│  做〔守卫〕装备〔枪〕                    ● 保持
│  做〔守卫〕前往〔防御点〕                 ●
│  做〔守卫〕持续攻击〔最近的敌人〕           ● 直到没有敌人
└ 每 30 秒最多触发一次 · 优先级 50
```

- `〔…〕` 是可点击的实例槽
- `🔍` 点开会在游戏里高亮所有候选（幽灵图标），你亲眼确认选对没
- `●` 是状态灯：绿/黄（重试中）/红（失败，点开看原因）
- 「保持」= 维持型动作，被打断自动恢复

### 温度例子（非 Pawn，一样的形式）

```
┌ 当〔天气 = 下雨〕且〔餐厅温度 < 10℃〕持续 10 秒 ──
│  做 打开〔餐厅的加热器〕
│  做 直到〔餐厅温度 > 15℃〕才停止     ← 滞回，默认自动生成
└ 每 1 分钟最多触发一次
```

注意「持续 10 秒」和「直到 > 15℃」——**这两个是电平触发/滞回的可视化表达**，玩家不需要理解这两个词。引擎默认就加，滑块可调。

### 专家层（点「▸高级」展开同一个规则）


## 三、让"至少像 Scratch 一样简单"真正成立的杀手功能

Scratch 之所以简单，是因为它没有失败、没有并发、没有自主 AI。你要把这些藏起来，最好的办法不是做文档，而是：

- **试运行（Dry Run）**：对当前存档模拟跑一遍，**不改任何状态**，只输出「会发生这些事」。玩家敢点试运行，才敢开自动执行。

## 四、块语法的形状约定

用**形状**代替类型说明，这是 Scratch 最成功的一点：

| 形状 | 含义 | 颜色 |
|---|---|---|
| 帽子（圆顶） | 触发：事件 / 电平 | 橙色 |
| 六边形（缺口） | 条件（布尔） | 蓝色 |
| 圆角（椭圆） | 值（数/文本/坐标） | 绿色 |
| 方块（凸起） | 动作 | 紫色 |
| C 型（夹口） | 控制流：如果/重复/直到 | 灰色 |
| `$变量` | 绑定结果，可拖到任何同类型槽 | 黄色 |

**同类型槽才吸附**，拖过去颜色不匹配直接弹回。这比报错好一万倍。

另外「ECA 变成 mod 加载器」那点：区别在**颗粒度**。mod 是作者写死的整体；规则包是玩家可拆可组的数据（像 Factorio 蓝图 vs mod）。所以这两者不是竞争关系，规则包可以调 mod 的接口。这点你想的方向没错。

## 四、一个真问题：GPL-3.0 和你的目标打架了

你说两件事：

1. 别的 mod 引用它、省一堆代码 → **成为他人依赖的库**
2. 本体 **GPL-3.0**

GPL-3.0 的传染性针对"基于本程序的作品"。别的 mod 调用你的 DLL 的类/接口，实务上会被认定为衍生作品 → **那个 mod 也必须 GPL-3.0**。RimWorld 社区里大量作者不接受这个条款，会直接放弃集成你。

三选一：

| 方案 | 效果 |
|---|---|
| **LGPL-3.0** | 别人可以任意许可证依赖你；你库本身的修改必须开源。**最契合你"给别人当底座"的目标** |
| GPL-3.0 + 链接例外 | 等价于 LGPL，但法律文本自己写，容易写错 |
| 坚持 GPL-3.0 | 生态里只剩愿意 GPL 的作者，框架价值打折 |

好消息：**规则包（数据文件）不是衍生作品，可以任意许可**。所以分享生态不受影响，只有"引用 API 的 mod"受影响。

这个不用现在定，但别等有 20 个 mod 集成了再改——改不了。

## 1. 用 `LGPL-3.0-or-later`，别用 `-only`

## 纯 C# 写

```csharp
public class CompProperties_SunChargedMech : CompProperties
{
    public float minGlow = 0.5f;
    public float ratePerRareTick = 0.01f;
    public CompProperties_SunChargedMech() => compClass = typeof(CompSunChargedMech);
}

public class CompSunChargedMech : ThingComp
{
    public CompProperties_SunChargedMech Props => (CompProperties_SunChargedMech)props;

    public override void CompTickRare()   // 250 tick 一次，不是每 tick
    {
        var p = parent as Pawn;
        if (p == null || p.Dead || p.Downed || p.MapHeld == null) return;

        // 注意：UI 上显示 50，底下是 0~1 的浮点
        if (p.MapHeld.glowGrid.GroundGlowAt(p.PositionHeld) < Props.minGlow) return;

        var energy = p.needs?.TryGetNeed<Need_MechEnergy>();  // 名字示意
        if (energy == null || energy.CurLevel >= 0.99f) return;  // 幂等

        energy.CurLevel += Props.ratePerRareTick;
    }
}
```

加上一个 XML 把它挂到机械族的 ThingDef 上，再加条本地化。**总共大概三四十行。**

不是"难不难"。这三十行对一个熟手是三十分钟的事。

**差别是：谁能做，以及改一次要多久。**

| | C# | 规则 |
|---|---|---|
| 谁能做 | 会写 mod 的人 | 任何玩家 |
| 阈值从 50 改成 30 | 改代码 → 编译 → 重启游戏 → 读档 | 改一个数字，立即生效 |
| 和"温度低于 10 就回室内"叠加 | 再写一段 | 再加一块 |
| 分享给别人 | 一个 DLL，算另一个 mod | 一段数据，聊天里就能贴 |

第三行是规则系统最实在的卖点。**凡是靠调参数的玩法，迭代速度的差别会要命。**

"加电量"这个动作，是某个 mod 作者写了一次 `CompSunChargedMech`、然后把它暴露成动作原语。你的系统省的不是那三十行，是**那三十行被摊薄了一万次**。

这有直接后果：

- 你的表达能力 = 你（和生态）提供的动作词汇表。词汇表里没有的，玩家只能等。
- 所以"动作怎么扩展"是核心 API 问题，不是细节。能不能只用 Def + 一小段执行器就加一个新动作？如果加动作必须改引擎，那你的框架会跟着你的发版节奏走，生态起不来。
- 对付这一点，值得把动作分成两层：**通用动作**（下 job、去某处、拿某物、开某物）由引擎提供；**专用动作**（加电量、改温度、生成物品）由第三方注册。前者覆盖 80% 的玩法，后者负责长尾。

## 这个例子真正暴露的技术难点：订阅

光照变化**没有原生事件**。屋顶盖上去、门开开关关、太阳耀斑、建造、拆除、昼夜推进，都会改 `glowGrid`。你要让"光照 > 50"实时重评估，就得在引擎侧找个地方挂上去——大概率是 GlowGrid 重算的路径，或者地图的 rare tick 里做脏格子检查。

**这是你整个系统里唯一可能被迫轮询的地方。**处理不好，"不轮询"就只是规则层不轮询，引擎层在偷偷每 250 tick 扫一遍。250 tick 扫全图光照勉强能忍，扫全图实体就完蛋。

所以这里要定的设计是：**订阅层怎么知道哪些格子该被观察？**最省的做法是"有人订阅了某格的光照，才把它加进观察集合"，没人订阅就完全不看。这跟 UI 里的暗角刷新是同一个套路。

## 顺带两个语义坑

**一、"亮的地方"不等于"室外"。**玩家会以为室外就亮，但屋顶、树荫、山体都会挡。所以条件写 `光照 > 50`，实际算的是格子上的值。你的规则预览必须能直接告诉玩家"这格现在是 37"，否则他会一直怀疑规则坏了——这就是哑 bug 的典型形态。

**二、别和原版充电桩打架。**机械族在充电桩里时原版已经在恢复能量了，你再 God 加一次就是双倍。要么规则只做"去有光的地方等着"，要么 God 动作要显式声明"忽略充电桩状态"。这类冲突正是"原版第一顺位"要处理的东西。

## 建议

**把这条当成第一个验收标准。**它能跑起来，说明电平条件、订阅、幂等、能力匹配、顺位五件事都活了，后面加触发器只是加法。跑不起来，别急着加功能。

比它更适合当 canary 的只有你自己举的那个——"袭击来了，在外面的人回家"。两个一起做，一个测边沿触发，一个测电平条件。

## Assistant

理解你的意思了：God 侧的动作表直接对着原版 DevMode 来薅。`DebugAction` 本身就是一个几百条静态方法的动作库，带分类、带参数类型、带"允许的游戏状态"，反射一遍就能在第一天拿到一个巨宽的词汇表。这个判断是对的。

而且执行侧真正需要的 Harmony 确实比直觉少，因为 vanilla 给的扩展点够多，形式都是"注册进去"而不是"拦下来"：

- 想让人做事 → `JobDriver` + `jobs.TryTakeOrderedJob`，不用 patch
- 想让某类 pawn 自发做事 → `JobGiver` / XML 插 think tree，不用 patch
- 想周期性看点什么 → `MapComponent` / `GameComponent`，不用 patch
- 想挂数据/开关 → `DefModExtension` + `PatchOperation`，不用 patch

**但代价在别处：采样。** 你没有事件，就得周期性地看。所以"少 Harmony"的反面是"多少采样"，这才是你架构里真正的预算项。

我的建议是在 condition 上直接写一个 `maxStaleness`（250 tick / 2000 tick 之类），引擎按档位分桶采样。好处是玩家能看懂"这条规则每秒查 4 次"，你能在引擎里统一节流，而不是每个条件自己去挖 hook。只有真的需要边沿语义的（"崩溃刚开始那一刻"）才单独给 patch。

判据就一句：**有边沿语义 + vanilla 没有扩展点 → patch；只是电平条件 → 采样。**

拿你举的例子过一遍：

- "袭击信封弹出" → 扫 `Find.LetterStack.LettersListForReading`，小列表，rare tick 足够，不 patch
- "光照 > 50" → 采样 `GlowGrid.GroundGlowAt`，不 patch
- "电量 < 99%" → 采样 need，不 patch
- "建筑毁坏" → 这条得 patch `Thing.Destroy`。想用 lister 做差集的话，rare tick 上全图 thing 比对会痛，所以这一条属于那"几个"里的一个

真正值得 patch 的其实是**没有扩展点的状态突变**：`Thing.Destroy`（顺手覆盖建筑毁坏、物品消失、pawn 尸体）、`TryStartMentalState`（崩溃开始）、drafted 的 setter（玩家接手）、downed 的 setter。这几个挂上去，"突变的瞬间"基本就齐了，加起来个位数。规模和你说的"几个 patch"对得上。

不过有个反直觉的地方你得接受：**Harmony 崩得响，采样错得哑。** patch 挂了会进 log 有 stacktrace，采样挂了只是值不新鲜、规则不触发，玩家只会觉得"有时候不灵"。所以"少 Harmony"不是纯赚，你是把风险从显性崩溃挪到了隐性不灵。缓解还得靠日志——必须能看出"这个条件上次求值是什么时候、值是多少"。

薅 `DebugAction` 有两个坑，现在就得定：

一是**破坏性动作必须分级**。那里面什么都有：生成袭击、秒杀 pawn、删建筑。全开给玩家就是灾难。薅过来的动作要自动打标签（能不能撤、影响范围、是否越过原版权威），默认只暴露安全子集，危险的走开发者 tier + 二次确认。

二是**它们不是稳定 API**。反射到的是内部实现，版本一改就烂。中间必须隔一层适配器——自己的动作 ID + 参数签名，一个动作烂了只标灰加日志，不能带崩引擎。别让反射结果直接进规则定义。
